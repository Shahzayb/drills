bottom, one line each. A line is added when a plan file is created (status `planned`) and
updated (or a new line added) when the implementation lands (status `implemented`). This is
a log, not a summary — for current state and reasoning see `progress.md` and `techContext.md`.

The description column carries the decision or result that would otherwise take re-reading
the whole plan to recover — not just the topic. See `SKILL.md` for what that means in practice.

| 2026-08-13 | [drill-05-load-test-baseline](../plans/2026-08-13_drill-05-load-test-baseline.md) | k6 baseline for `GET /conversations` — the `before` column cards 08/09/10 get compared against, from the client's side rather than `EXPLAIN`'s. 10 VUs closed-loop, 20s warm-up excluded via a second scenario, 60s measured, 3 runs each. | 2026-08-13 | [drill-06-request-id-propagation](../plans/2026-08-13_drill-06-request-id-propagation.md) | One request id threaded browser → Next → Nest → Postgres/Redis, all logs converted to structured JSON via pino + nestjs-pino. Correlation, **not** tracing — the OTel stretch is a separate phase in the same plan file, landed after this A/B since auto-instrumentation moves latency. Key decisions: the id is memoised on the request via a symbol key so `genReqId` and the middleware can't disagree on ordering; inbound `x-request-id` is allowlisted `^[A-Za-z0-9_-]{8,64}$` because it lands in a SQL comment and `pg` sends param-less queries over the *simple* protocol, where `;`-separated statements are legal; ALS context is entered in **middleware, not the interceptor**, since `next.handle()`'s Observable subscribes outside any `als.run()` wrapping; `application_name`/`CLIENT SETNAME` were rejected as per-connection on pooled singletons. Postgres statement logging is a runtime toggle, not always-on, so drill 05's baseline is unchanged. **Result:** one grep returns every service's lines for a request; e2e suite green. Drill 05's pool-oversubscription finding upgraded from inference to observation — the two `Promise.all` queries of one request run on two different Postgres backend PIDs. **The overhead is a fixed ~0.9ms/request, not a percentage**: tail org (2ms requests) loses 27-35% throughput across silent/info/debug logging; whale org (176ms requests) shows no measurable effect at all. Biggest self-inflicted bug, found by measuring: **a suppressed log line still evaluates its arguments** — a regex ran on every call regardless of level; `isLevelEnabled` guards recovered 5-6%, 0% at debug as predicted. Review caught four more bugs: pino-http logs 5xx at `info` without `customLogLevel`; `customProps` applied twice duplicates a JSON key; `exclude` drops request context where `autoLogging.ignore` doesn't; a thrown query logs `rows: null`, reading as an empty result. | implemented |
| 2026-08-13 | [drill-06-request-id-propagation](../plans/2026-08-13_drill-06-request-id-propagation.md) | Phase 2: OpenTelemetry spans + a local collector + Jaeger, behind `OTEL_EXPORTER_OTLP_ENDPOINT` and `profiles: ['trace']` so drill 05's baseline stays untouched. `NodeSDK` on both sides — five named instrumentations on the API, **zero** on the web (Next emits its own spans; the only missing piece is the outgoing `traceparent`, injected by hand in `lib/api.ts`). **Headline result:** a `db_query` line said the count query took 7.9ms; the trace showed 5.48ms of that was `pg-pool.connect` (4.53ms opening a new socket), 2.09ms executing — drill 05's pool finding now has a number. Found only by reading output: `@vercel/otel` was dropped for the same `NodeSDK` (needless peer deps); Next does not propagate `traceparent` on outgoing fetch; **Next runs `proxy.ts` in its own one-span trace**, so minting the request id from the active trace id at the edge pointed at the wrong trace — `trace_id` on every log line replaced that plan; and **our `/* rid= */` SQL comment and sqlcommenter are mutually exclusive**, so phase 1 had silently disabled the standard one — the comment now trails and stands down when tracing is on. **Cost, interleaved 3 arms x 2 rounds, tail org:** off 3,121 req/s → 5% sampled 2,124 (−32%) → 100% sampled 1,729 (−44.6%); within-arm spread 2-4%. Two traps: pnpm 11 fails `install --frozen-lockfile` on an undecided build script; Jaeger all-in-one keeps traces in RAM and was SIGKILLed by its 1g limit at 100% sampling. | 2026-08-15 | [drill-07-tenant-isolation](../plans/2026-08-15_drill-07-tenant-isolation.md) | Four new conversation endpoints ship **filterless on purpose**; what scopes them is **Postgres RLS** with a transaction-local `app.org_id`, served by a non-superuser `app_user` role — chosen over a repository layer because `PostgresService` is `@Global()` and a TS seam protects only code that opts in. 18 adversarial cases; **14 fail when the policies are dropped**, proving the mechanism. **Cost, 26 interleaved runs:** a fixed ~0.94ms/request — tail org (3ms requests) −23.5% throughput, whale org (185ms) unmeasurable. **The policies themselves are free**; every measurable cost is the `BEGIN`/`set_config`/`COMMIT` wrapper. The whale should have lost ~33ms from serialising `Promise.all` and only lost ~8.5ms, because one connection per request removes drill 05's 2:1 pool oversubscription — the effects cancel. The rejected repository-layer alternative was measured too: free, within noise — it lost on test coverage, not speed. Biggest finding: **`PARALLEL SAFE` on the policy function is worth 2.4x** (whale count 42.7→108.0ms, list 88.9→214.7ms) — SQL functions default to `PARALLEL UNSAFE` and an unsafe policy predicate serialises every query on that table; `STABLE` additionally folds the policy into a One-Time Filter and preserves the index-only scan. Traps: the app had been a **superuser** for six drills (RLS would have been theatre); a transaction-local GUC reverts to `''` not NULL, so `nullif` is what keeps it fail-closed; node-pg-migrate echoes every statement, password included. Method note: the `before` arm was **discarded** — 33% spread because it was the only arm whose process restarted, so arms must differ only in the variable. | implemented |
