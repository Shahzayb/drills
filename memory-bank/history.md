# History

Every plan and implementation, in chronological order. Append-only — new entries go at the
bottom, one line each. A line is added when a plan file is created (status `planned`) and
updated (or a new line added) when the implementation lands (status `implemented`). This is
a log, not a summary — for current state and reasoning see `progress.md` and `techContext.md`.

The description column carries the decision or result that would otherwise take re-reading
the whole plan to recover — not just the topic. See `SKILL.md` for what that means in practice.

Result: 104.3s seed against a 6-minute budget, 3.2GB on disk. | 2026-08-12 | [seed-simplification](../plans/2026-08-12_seed-simplification.md) | Finishes drill-04's "measured and reverted" pass: reverts the three Node-side hot paths it *kept* (HEX table, day cache, template pre-compiler — 9.7s of CPU), plus the 5-flag lever matrix and the triplicated structure COPYs. The four SQL levers all stay — measured as seconds paid per line removed, the Node-side code is ~0.12 s/line against the FK lever's ~5.1, and the levers are also what the drill teaches. Key property: every change is fingerprint-preserving, so all five recorded table hashes must come back unchanged — a data-identity proof across 12.5M rows, not just a passing test suite. Result: 108.21s vs 108.2s before, all five hashes unchanged, non-comment code 554 → 472 lines. The bench confirms the mechanism — generation fell from ~2M to 1.11M bodies/s and stayed 8.7× ahead of Postgres's 127k rows/s, so 9.7s of CPU bought ~0s of wall clock. Watch out: the first run read 114.24s and a single measurement would have reported a 5% regression that does not exist. | implemented |
