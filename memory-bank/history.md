# History

bottom, one line each. A line is added when a plan file is created (status `planned`) and
updated (or a new line added) when the implementation lands (status `implemented`). This is
a log, not a summary — for current state and reasoning see `progress.md` and `techContext.md`.

The description column carries the decision or result that would otherwise take re-reading
the whole plan to recover — not just the topic. See `SKILL.md` for what that means in practice.

| 2026-08-13 | [drill-06-request-id-propagation](../plans/2026-08-13_drill-06-request-id-propagation.md) | One request id threaded browser → Next → Nest → Postgres/Redis, all logs converted to structured JSON via pino + nestjs-pino. Correlation, **not** tracing — no spans, no sampling; the OTel stretch is scoped as a separate phase in the same plan file and must land after the A/B below, because auto-instrumentation moves latency. Four decisions worth keeping: the id is memoised on the request with a symbol key so `genReqId` and our middleware can't disagree about ordering; an inbound `x-request-id` is allowlisted `^[A-Za-z0-9_-]{8,64}$` because it lands in a SQL comment and `pg` sends param-less queries (e.g. `/health`'s `SELECT 1`) over the *simple* protocol, where `;`-separated statements are legal — the injection is real, not theoretical; the ALS context is entered in **middleware, not the interceptor**, because `next.handle()` is a lazy Observable that subscribes outside any `als.run()` wrapping the pre-phase; and `application_name`/`CLIENT SETNAME` were rejected as per-connection on pooled singletons (2 extra round trips per request). Postgres statement logging is a runtime toggle (`db:log:on`/`off`), not always-on, so drill 05's instrument is unchanged — watch out, `ALTER SYSTEM` persists in the volume across restarts. Checked rather than assumed: Next 16 renamed `middleware.ts` → `proxy.ts`; `forRoutes('*')` *is* fine on Nest 11 (`legacy-route-converter.js` rewrites it to `{*path}` and suppresses the warning); `LoggerModule` is `@Global()` so re-importing it doubles every log line. **Result:** one grep returns 12 lines across 3 services; 27 e2e tests pass. Drill 05's finding #2 confirmed and upgraded from inference to observation — the two `Promise.all` queries of one request are executed by two different Postgres backend PIDs. The overhead is a **fixed ~0.9ms/request, not a percentage**: tail org (2ms requests) −26.7% throughput with logging *silent*, −30.7% info, −34.7% debug; whale org (176ms requests) **no measurable effect at all** — "before" landed between two "after" runs on every metric, and those runs reproduce drill 05's baseline (48.02 vs 48.57 req/s). So the plumbing costs ~4x what the logging costs, and a percentage overhead is meaningless without saying what it is a percentage of. Biggest self-inflicted bug, found by measuring rather than reading: **a suppressed log line still evaluates its arguments** — `summarise(text)` ran a regex per statement at every level, including `silent`; `isLevelEnabled` guards recovered 6.0%/5.0% and, as predicted, 0% at debug. Review caught four more: pino-http logs every 5xx at `info` without `customLogLevel`; `customProps` is applied twice so a mid-request field emits a duplicate JSON key with two values; `exclude` drops the request context where `autoLogging.ignore` does not; and a thrown query logged as `db_query` with `rows: null` reads as an empty result set. | implemented |
| 2026-08-13 | [drill-06-request-id-propagation](../plans/2026-08-13_drill-06-request-id-propagation.md) | Phase 2, the card's stretch: OpenTelemetry spans + a local collector + Jaeger, all behind `OTEL_EXPORTER_OTLP_ENDPOINT` and `profiles: ['trace']` so drill 05's instrument is untouched. `NodeSDK` on both sides — five named instrumentations on the API, **zero** on the web (Next already emits its own spans through `@opentelemetry/api`, which it declares as a peer; the only missing piece is the outgoing `traceparent`, which Next does *not* inject, so `lib/api.ts` calls `propagation.inject` by hand). **Headline result:** a `db_query` line said the count query took 7.9ms; the trace says 5.48ms of that was `pg-pool.connect` (4.53ms of it opening a new socket) and 2.09ms was executing. Drill 05's finding #2 has now gone inference → observation (two backend PIDs) → **a number**. Four things the plan got wrong, all found by reading output: `@vercel/otel` dropped for the same `NodeSDK` (7 peer deps for a tier that needs no instrumentations); Next does not propagate `traceparent` on outgoing fetch; **Next runs `proxy.ts` in its own one-span trace**, so minting the request id from the active trace id at the edge produced a valid, greppable id pointing at the wrong trace — the plan's "one id" join died there, and `trace_id` on every log line replaced it; and **our `/* rid= */` SQL comment and sqlcommenter are mutually exclusive** — `@opentelemetry/sql-common` refuses to comment a statement that already has one, so phase 1 silently disabled the standard. Also: a *leading* comment renamed every query span to `pg.query:/*`, since instrumentation-pg takes the first whitespace-delimited token — hence the comment now trails and stands down entirely when tracing is on. **Cost, interleaved 3 arms x 2 rounds, tail org:** off 3,121 req/s (p50 3.05ms) → 5% sampled 2,124 (−32.0%) → 100% sampled 1,729 (−44.6%); within-arm spread 2.1–3.9%. So **dropping 95% of traces buys back only 28% of the cost** — the rest is the instrumentation, which runs whether the span is kept or not. That is phase 1's "the plumbing costs more than the output" finding a second time, and it means the lever is fewer instrumentations, not a lower sample rate. Two traps for the next session: pnpm 11 fails `install --frozen-lockfile` on an undecided build script (`allowBuilds: { protobufjs: false }`), and Jaeger all-in-one keeps traces in RAM and was SIGKILLed by its 1g limit at 100% sampling. One thing I suspected and measured wrong: the collector's `debug` exporter at `verbosity: normal` (~10k lines/s) looked like an obvious confound and was not — the `normal` run came out marginally faster. | implemented |
| 2026-08-15 | [drill-07-tenant-isolation](../plans/2026-08-15_drill-07-tenant-isolation.md) | Four new conversation endpoints ship **filterless on purpose** and stay that way; what scopes them is **Postgres RLS** with a transaction-local `app.org_id`, served by a non-superuser `app_user` role. The **policies are free** (`rls-on` − `txn-only` = −0.9%); every measurable cost is the `BEGIN`/`set_config`/`COMMIT` wrapper — drill 06's "the plumbing costs more than the output" a third time. Biggest finding beats the k6 table: **`PARALLEL SAFE` on the policy function is worth 2.4x** (whale count 42.7→108.0ms, list 88.9→214.7ms) because SQL functions default to `PARALLEL UNSAFE` and an unsafe policy predicate makes every query on that table serial; the `STABLE` marking also folds the policy into a **One-Time Filter** and preserves the index-only scan. Three traps: the app had been a **superuser** for six drills (RLS would have been pure theatre, and `FORCE` does not fix it); a transaction-local GUC reverts to **`''` not NULL**, so the `nullif` is what keeps it fail-closed instead of a 500 on every later unscoped query; and **node-pg-migrate echoes every statement**, password included. Method note worth reusing: the `before` arm was **discarded** — 33% spread because it was the only arm whose process restarted, so arms must differ only in the variable. | implemented |
